# ADR-0002: パケットではなく OS が再構成した TCP ストリームを観測境界とする

## 状態

採用

## 背景

TcpTap は、クライアントと中継先の間に TCP 中継ツールとして配置されます。Java の `Socket` から読み取れるのは、OS の TCP スタックが順序制御・再送処理などを終えた後のバイトストリームであり、元の IP/TCP パケットそのものではありません。

TcpTap の観測機能やキャプチャ出力でこの事実を曖昧にすると、パケット損失、再送、TCP ウィンドウ、実パケットの時刻などを解析できるように誤認されます。

一方、TcpTap は入力ストリームから正常に読み取ったアプリケーションのバイトストリーム、エンドポイント、セッションのライフサイクルを直接かつ環境に依存せず観測できます。読み取った後に反対側への書込みが失敗する場合があるため、観測した事実と中継に成功した事実は同一ではありません。

## 決定

TcpTap の標準的な観測境界を、Java `Socket` の TCP バイトストリームとします。

- ペイロードは、入力ストリームの `read()` が正常に返した時点で TcpTap が観測した事実として扱う。
- 観測済みペイロードは、その後の反対側への `write()` 成功を条件にせずキャプチャ対象とする。
- 中継に成功したバイト数は、反対側への `write()` が正常に完了したバイト数として別に扱う。
- ペイロードはアプリケーションプロトコルとして変更せず、そのまま中継する。
- 読取りバッファの境界を、TCP パケット境界またはアプリケーションメッセージ境界とみなさない。
- パケット単位のメタデータを、標準の中継処理から推測しない。
- キャプチャファイルを生成する場合は、再構成したパケット表現と実際のパケットキャプチャを明確に区別する。
- ネイティブのパケットキャプチャを標準動作の前提にしない。

## 影響

Npcap / libpcap、管理者権限、NIC の選択に依存せず、Java だけで環境依存の少ない観測機能を実装できます。

Wireshark などへ渡すキャプチャ表現を生成する場合も、アプリケーションストリームの解析には使えますが、TCP のトランスポート層における障害解析には使えません。また、キャプチャに含まれるペイロードは TcpTap の観測点で見えたことを表し、反対側アプリケーションへの配送成功を証明しません。

## 見直し条件

実パケットのシーケンス番号、再送、ウィンドウ、ネットワーク上の実時刻などを取得すること自体が TcpTap の中心要件になった場合。その場合も、ストリーム中継とパケットキャプチャは別の観測源として設計します。
