# TcpTap ドキュメント構成

このディレクトリの文書は、TcpTap を仕様駆動で変更するための現在有効な正本です。

仕様駆動のための ID や追跡可能性は重要ですが、**設計書そのものは、人間が上から読んで理解しやすい一般的なソフトウェア設計書の章立てを優先**します。仕様 ID・受入条件・テスト対応表は、設計内容を分類するための主軸ではなく、変更・レビュー・テストを追跡するための補助情報として扱います。

## 1. 文書体系

| 文書 | 正本として扱う内容 | 書かない内容 |
| --- | --- | --- |
| [`../README.md`](../README.md) | 利用者向け概要、導入、基本的な使い方 | 詳細仕様、内部構造、開発手順 |
| [`EXTERNAL_DESIGN.md`](EXTERNAL_DESIGN.md) | CLI、入出力、ネットワーク上の挙動、ファイル、観測可能なイベント、セキュリティ境界など、外部から観測可能な現在仕様 | Java クラス、スレッド API、非公開の実装詳細 |
| [`INTERNAL_DESIGN.md`](INTERNAL_DESIGN.md) | アーキテクチャ、コンポーネント／クラス、処理方式、データ／状態、並行処理、リソースの所有関係、エラー処理など | 利用者向け説明、偶然そうなっているだけの非公開実装詳細 |
| [`OPERATIONS.md`](OPERATIONS.md) | ビルド、テスト、配布物作成、リリース手順 | 製品仕様、設計判断 |
| [`adr/`](adr/) | 現在有効な重要な設計判断の理由と見直し条件 | 外部・内部仕様の重複記載 |
| [`../AGENTS.md`](../AGENTS.md) | AI／開発者が上記を維持するための作業規則 | 製品仕様の正本 |

文書間に矛盾がある場合は、ソースコードやテストから仕様を推測して確定せず、まず正本側の矛盾を解消します。

## 2. 設計書の構成原則

### 2.1 人間が読む順序を優先する

外部設計書・内部設計書は、ID 順、クラス名順、テスト順には並べません。

一般的なソフトウェア設計書と同様、読者が次の順で理解できる構成を基本とします。

```text
何を設計する文書か
    ↓
システム／ソフトウェア全体像
    ↓
構成・インターフェース
    ↓
主要処理
    ↓
データ／状態／入出力
    ↓
エラー／セキュリティ／非機能
    ↓
検証・追跡可能性
```

仕様 ID は該当する章・節に併記します。仕様 ID だけをまとめた巨大な一覧を設計本文の中心にはしません。

### 2.2 外部設計書の標準章立て

TcpTap のような CLI ソフトウェアでは、`EXTERNAL_DESIGN.md` を原則として次の順序で構成します。

1. **本書について**
   - 目的
   - 対象範囲
   - 関連文書
2. **システム概要**
   - ソフトウェアの目的
   - 利用範囲・対象外
   - システム境界
   - 動作環境
3. **CLI／ユーザーインターフェース仕様**
   - 実行形式
   - オプション／引数
   - 既定値
   - 入力検証
   - 終了コード
4. **通信・外部インターフェース仕様**
   - 待受処理
   - 中継先
   - 接続／タイムアウト
5. **主要機能・処理仕様**
   - 中継
   - EOF／ハーフクローズ
   - セッションの挙動
6. **出力・ログ仕様**
   - 標準出力
   - 標準エラー
   - 観測可能なイベント
7. **ファイル仕様**
   - ファイルのライフサイクル
   - 形式
   - キャプチャ内容
8. **異常系・エラー仕様**
   - 起動エラー
   - セッションエラー
   - ファイル／キャプチャエラー
9. **非機能・セキュリティ・制約**
   - 実行環境の互換性
   - セキュリティ／信頼境界
   - 性能／規模の制約
   - 利用上の制約
10. **受入条件**
11. **仕様・テスト対応表**

ソフトウェアの性質上不要な章は、空のまま残さず省略・統合して構いません。一方、エラーが複数機能に分散する場合は、各機能章で詳細を記載したうえで、横断的なエラー方針をまとめても構いません。

### 2.3 内部設計書の標準章立て

`INTERNAL_DESIGN.md` は原則として次の順序で構成します。

1. **本書について**
   - 目的
   - 対象範囲
   - 関連文書
2. **設計方針・全体構成**
   - アーキテクチャ
   - 設計方針
   - 依存方向
3. **パッケージ／コンポーネント／クラス設計**
   - パッケージ構成
   - コンポーネントの責務
   - クラスの責務
4. **処理設計**
   - 起動処理
   - 正常系の処理フロー
   - セッションの処理フロー
   - 異常系の処理フロー
5. **データ／状態設計**
   - モデル
   - 状態遷移
   - 不変条件
6. **並行処理・同期設計**
   - スレッドモデル
   - 共有状態
   - 同期
7. **入出力・通信・ファイル設計**
   - CLI 解析
   - ソケット入出力
   - ファイル形式／書込み処理
8. **例外・エラー・ログ設計**
   - 例外伝播
   - 障害の分離
   - ログ／観測性
9. **リソース・ライフサイクル設計**
   - 所有者
   - 生成／終了
   - 後始末
10. **依存関係・実行環境設計**
11. **内部不変条件・実装上の制約**
12. **外部仕様・テストとの追跡関係**

内部設計書をクラス一覧だけの文書にはしません。クラスはアーキテクチャと処理を実現する手段として位置付け、**処理フロー、状態、並行処理、リソースの所有関係を人間が理解できること**を重視します。

### 2.4 設計単位の標準記述様式

一般的な企業向け設計書としてレビューしやすくするため、外部設計・内部設計の主要な機能章または設計単位の先頭には、原則として次の「設計単位サマリ」を置きます。

| 項目 | 記載内容 |
| --- | --- |
| 目的 | その章・設計単位が何を定義し、何を保証するか |
| 入力・前提 | 処理開始条件、利用者からの入力、外部状態、上位設計から受け取る条件 |
| 処理・規則 | 維持すべき主要な振る舞い、判断規則、順序、不変条件 |
| 出力・結果 | 外部から観測できる結果、生成物、状態変化、下位コンポーネントへ渡す結果 |
| 異常系 | 失敗条件、影響範囲、継続／終了の扱い、例外・エラーの境界 |
| 関連仕様 ID | `EXT-*`, `INT-*`, `AC-*` のうち、その設計単位を追跡するために必要なもの |

記載上のルールは次のとおりです。

- 設計単位サマリは、本文を ID 順に並べ替えるためのものではなく、**章を読む前に設計の骨格を把握するための索引**として使う。
- サマリの下で、オプション一覧、処理順序、状態遷移、エラー一覧、データ項目などを表・箇条書き・フロー図で詳細化する。
- 同じ内容を各下位節へ機械的に重複させない。章全体で一つのサマリにまとめられる場合は、下位節では詳細だけを書く。
- 外部設計の「入力・前提」「出力・結果」は、利用者、接続相手、OS、標準入出力、生成ファイルなどから観測可能なものに限定する。Java クラスや非公開 API は書かない。
- 内部設計の「入力・前提」「出力・結果」は、コンポーネント間の責務、処理開始条件、状態、所有権、データの受渡しを記載できるが、外部仕様を詳細に複製しない。
- 順序が意味を持つ処理は番号付きリスト、候補・条件の列挙は箇条書き、項目ごとの比較や契約は表を優先する。
- 該当しない項目を無理に作らない。異常系が存在しないこと自体が設計上重要な場合は `なし` と明示する。
- `関連仕様 ID` は追跡のための補助情報であり、本文の意味を ID だけで表現しない。

## 3. 外部設計と内部設計の境界

### 3.1 外部設計に書くもの

実装方式を全面的に変更しても、利用者、接続相手、OS、生成ファイル、標準出力／標準エラーから観測できる契約を記載します。

代表例:

- CLI オプション、既定値、入力検証、終了コード
- 待受処理／中継先の接続動作
- 中継、EOF、ハーフクローズ、エラー時の外部動作
- 標準出力／標準エラーの意味と形式
- ファイルの作成／上書き／失敗時の動作
- pcapng の意味と制約
- 実行環境の互換性
- セキュリティ／信頼境界
- 性能やリソース上限を外部契約にする場合の測定可能な条件

クラス名、非公開メソッド、バッファサイズ、`Thread` / `ExecutorService` などの具体的な API は、外部契約でない限り固定しません。

### 3.2 内部設計に書くもの

外部仕様を安定して実現するため、実装が維持すべき設計を記載します。

代表例:

- アーキテクチャ／依存方向
- コンポーネント／クラスの責務
- 起動／終了／セッションのライフサイクル
- 処理フロー
- 状態／データ構造
- 並行処理モデル
- ソケット／ストリーム／書込み処理のリソース所有関係
- 例外伝播／障害の分離
- 外部仕様と実装コンポーネントの対応

非公開ヘルパーの名前、ローカル変数、単純なメソッド分割、意味を持たない定数などは、設計上の制約でない限り記載しません。

## 4. 仕様駆動の変更フロー

機能・挙動・内部構造を変更するときは、原則として次の順序で進めます。

```text
Issue／利用者からの要求
       |
       v
外部から見える挙動を分析
       |
       +-- 観測可能な挙動が変わる --> EXTERNAL_DESIGN
       |
       v
受入条件
       |
       v
内部設計を分析
       |
       +-- 維持すべき設計が変わる --> INTERNAL_DESIGN
       |
       +-- 重要な選択・理由 --------> ADR
       |
       v
テスト
       |
       v
本体コード
       |
       v
必要に応じて README／OPERATIONS
```

実装を先に変更し、その実装を説明するために設計書を後付けする運用にはしません。

## 5. 安定識別子

重要な契約を変更単位として追跡できるよう、安定した ID を付与します。

| 種別 | 形式 | 例 |
| --- | --- | --- |
| 外部仕様 | `EXT-<AREA>-NNN` | `EXT-NET-004` |
| 内部設計 | `INT-<AREA>-NNN` | `INT-LIFE-002` |
| 受入条件 | `AC-<AREA>-NNN` | `AC-CLI-001` |
| 未決事項 | `TBD-NNN` | `TBD-003` |
| ADR | `NNNN-<name>` | `0003-synthetic-pcapng-from-relayed-stream` |

`AREA` は必要以上に細分化しません。

- `ENV`: 実行環境／配布
- `CLI`: コマンドライン／終了コード
- `NET`: 待受処理／中継先への接続
- `RELAY`: バイトストリーム中継／EOF／エラー
- `OBS`: 標準出力／標準エラー／観測可能なイベント
- `FILE`: ファイルのライフサイクル
- `CAP`: pcapng／キャプチャ
- `SEC`: 信頼境界／セキュリティ境界
- `CMP`: コンポーネントの責務
- `LIFE`: ライフサイクル／リソースの所有関係
- `CONC`: 並行処理
- `ERR`: 内部エラー／障害の分離

ID は**章立ての代わりではありません**。該当する自然な章・節に付与します。

## 6. 仕様記述規則

### 6.1 規範表現

| 用語 | 意味 |
| --- | --- |
| MUST / MUST NOT | 必須／禁止。満たさない実装は仕様違反 |
| SHOULD / SHOULD NOT | 原則。外す場合は理由を明示する |
| MAY | 許容される選択肢 |

通常の日本語で同じ意味が明確なら、すべての文を MUST 形式へ書き換える必要はありません。

「適切に」「必要に応じて」「通常」「可能な限り」など、テスト可能な意味を決められない表現を中核仕様には使用しません。

### 6.2 TBD

未確定事項を実装または AI が推測して埋めません。

```text
TBD-001
決定事項: <決める事項>
影響範囲: <EXT / INT / AC ID>
決定期限: <実装・テストのどこまでに必要か>
```

## 7. 受入条件

外部仕様のうち、既存機能を壊すリスクが高いもの、複数コンポーネントにまたがるもの、CLI／ネットワーク／ファイルとして外部から検証できるものには `AC-*` を定義します。

受入条件は実装詳細ではなく、外部から観測できる結果で記述し、原則として次の表形式を使います。

| 項目 | 内容 |
| --- | --- |
| 受入条件 ID | `AC-NET-001` |
| 対象仕様 | `EXT-NET-004` |
| 前提 | 中継先が接続を拒否する |
| 操作 | クライアントが TcpTap の待受ポートへ接続する |
| 期待結果 | 当該セッションを終了する。待受プロセスは継続し、次のクライアント接続を受け付けられる。 |

複数の期待結果がある場合は、セル内で `<br>` を使うか、表の直後に箇条書きで詳細化します。

## 8. 追跡可能性

重要な仕様について、次を追跡できる状態を維持します。

```text
外部仕様
   |
   v
受入条件
   |
   v
内部設計／コンポーネント
   |
   v
テスト
   |
   v
本体実装
```

ただし、対応表は設計本文の途中へ分散させず、原則として設計書の末尾へまとめます。本文は、人間が設計を理解するための構成を優先します。

## 9. テストレベル

| 対象 | 主なテスト |
| --- | --- |
| CLI オプション／入力検証／終了コード | パーサー単体テスト、CLI 実行テスト |
| ネットワーク上の挙動／セッションのライフサイクル | ループバック結合テスト |
| 双方向中継／ハーフクローズ | ソケット結合テスト |
| pcapng のバイナリ仕様 | 独立したバイト単位の検証 |
| 内部不変条件 | コンポーネント／結合テスト。非公開処理の呼出順は固定しない |

外部仕様を実装に合わせるためだけに、テストの期待値を変更しません。仕様変更であれば、先に外部設計と受入条件を変更します。

## 10. 変更時チェックリスト

仕様・設計に関係する PR では、少なくとも次を確認します。

- 外部設計書・内部設計書の章立てが、人間の理解順になっているか。
- 主要な機能章／設計単位に、目的・入力／前提・処理／規則・出力／結果・異常系・関連仕様 ID を把握できるサマリがあるか。
- サマリと下位節で同じ内容を不必要に重複していないか。
- ID や追跡の都合で、同種の設計情報が離れた章へ分散していないか。
- 外部から観測できる変更なら、該当する `EXT-*` を更新したか。
- 回帰を防ぐ受入条件が必要なら、`AC-*` を更新したか。
- 責務、ライフサイクル、並行処理、リソースの所有関係が変わるなら、`INT-*` を更新したか。
- 重要な選択理由を将来も維持する必要があるなら、ADR を更新したか。
- `EXT -> AC -> INT -> test -> implementation` の対応を説明できるか。
- TBD を推測で解消していないか。
- README／OPERATIONS に同じ詳細仕様を複製していないか。
- 変更後に不要な仕様、設計、テスト、実装を残していないか。

## 11. この文書体系の対象範囲

文書量を増やすこと自体は目的ではありません。TcpTap は小規模な Java CLI であるため、独立した要求定義書、クラス一覧だけの詳細設計書、全メソッドの処理仕様書などを自動的には追加しません。

一般的なソフトウェア設計書の章立てと読みやすさを保ちながら、必要な契約にだけ安定 ID、受入条件、追跡関係を追加することで、人間の保守性と仕様駆動の両立を図ります。
