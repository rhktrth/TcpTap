# TcpTap 外部設計書

この文書は TcpTap の**現在有効な外部仕様の正本**です。外部仕様とは、利用者、接続するクライアント／中継先、生成されるファイル、標準出力／標準エラーから観測でき、内部実装を変更しても維持すべき契約を指します。

## 1. 本書について

### 1.1 目的

TcpTap の CLI、通信、中継、出力、キャプチャファイル、異常時の動作、非機能条件など、外部から観測可能な仕様を定義します。

Java クラス、非公開メソッド、バッファサイズ、スレッド API などの内部実装は本書では規定せず、[`INTERNAL_DESIGN.md`](INTERNAL_DESIGN.md) で扱います。

### 1.2 対象範囲

本書では次を扱います。

- CLI インターフェース
- 待受側／中継先との TCP 通信
- 双方向のバイトストリーム中継
- 標準出力／標準エラーと観測可能なイベント
- pcapng キャプチャファイル
- エラー時の外部動作
- 実行環境の互換性
- セキュリティ／信頼境界
- 利用上の制約

## 2. システム概要

### 2.1 目的と利用範囲

TcpTap は、クライアントと固定の中継先の間で TCP バイトストリームを双方向に中継し、中継処理自身が直接観測できるセッション情報を出力する軽量な TCP 中継ツールです。

必要に応じて、TcpTap が入力ストリームから直接観測したバイトストリームを再構成した擬似表現と、中継処理自身が確実に観測した診断イベントを、Wireshark で開ける pcapng として保存します。

大量接続を処理する高密度プロキシや、トランスポート層／ネットワーク層のパケット障害解析器は目的としません。

### 2.2 システム境界

```text
クライアント
  |
  | TCP バイトストリーム
  v
+---------+
| TcpTap  |
+---------+
  |
  | TCP バイトストリーム
  v
中継先

        +----------------------+
        | 任意の pcapng ファイル |
        +----------------------+
```

TcpTap は次を外部境界とします。

- アプリケーションのペイロードを変更しない。
- アプリケーションプロトコル固有のプロキシとして解釈・変換しない。
- OS の TCP スタックが再構成したバイトストリームを、中継と観測の境界とする。
- パケットスニファーとして、ネットワーク上の実パケットを採取・復元したものとは扱わない。
- ネイティブのパケットキャプチャドライバー／ライブラリを通常動作の前提にしない。
- 待受アドレスは安全側を既定とし、明示指定がない限りループバックだけにバインドする。
- TcpTap 自身には、クライアント認証・認可・接続元許可リスト・レート制限などのアクセス制御機能を持たせない。

## 3. CLI・ユーザーインターフェース仕様

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |
| 目的 | 利用者が TcpTap の待受先、中継先、接続タイムアウト、キャプチャ有無を一意に指定し、指定誤りを起動前に検出できる CLI 契約を定義する。 |
| 入力・前提 | `java -jar TcpTap.jar` に与える公開オプションとその値。 |
| 処理・規則 | 公開オプションだけを受け付け、既定値と値域を適用する。未知・重複・欠落・型変換不能・値制約違反を指定エラーとする。 |
| 出力・結果 | 有効な指定では待受処理へ進む。ヘルプでは使用方法を表示して正常終了する。終了コードは結果種別に応じて `0` / `1` / `2` とする。 |
| 異常系 | CLI 指定エラーでは待受処理を開始せず終了コード `2` とし、利用者向け出力へ Java のスタックトレースを表示しない。 |
| 関連仕様 ID | `EXT-CLI-001`, `EXT-CLI-002`, `EXT-CLI-003`, `AC-CLI-001` |

### 3.1 実行形式

```console
java -jar TcpTap.jar [OPTIONS]
```

### 3.2 公開オプション — `EXT-CLI-001`

| オプション | 値 | 既定値 | 契約 |
| --- | --- | --- | --- |
| `--listen-host <HOST>` | ホスト／ローカルアドレス | `127.0.0.1` | 空白だけの値を拒否する。前後の空白は除去する。 |
| `--listen-port <PORT>` | 整数 | `8080` | `1..65535` だけを受け付ける。 |
| `--dest-host <HOST>` | ホスト | `localhost` | 空白だけの値を拒否する。前後の空白は除去する。 |
| `--dest-port <PORT>` | 整数 | `80` | `1..65535` だけを受け付ける。 |
| `--connect-timeout <MILLIS>` | 整数 | `10000` | `1` 以上かつ Java `int` で表現できる値だけを受け付ける。単位はミリ秒。 |
| `--capture <FILE>` | パス | 無効 | TcpTap が観測したストリームの擬似表現と診断イベントを pcapng として新規ファイルに保存する。空白だけの値を拒否する。 |
| `-h`, `--help` | なし | - | ヘルプを表示する。 |

### 3.3 入力検証 — `EXT-CLI-002`

次は CLI の指定エラーとします。

- 未知のオプション
- 同じオプションの重複
- オプション値の欠落
- 型変換不能
- 3.2 の値制約に反する指定

公開オプション一覧にない旧オプション名などを、互換用の別名として扱いません。

### 3.4 ヘルプ・終了コード — `EXT-CLI-003`

`--help` / `-h` はヘルプを表示し、待受処理／中継処理を開始せず正常終了します。

| コード | 意味 |
| ---: | --- |
| `0` | ヘルプ表示などの正常終了 |
| `1` | 待受処理／キャプチャの初期化失敗、またはプロセス全体の実行エラー |
| `2` | CLI の指定エラー |

CLI の指定エラーと通常のプロセス全体のエラーでは、Java のスタックトレースを利用者向け出力へ表示しません。

## 4. 通信・外部インターフェース仕様

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |
| 目的 | 指定された待受アドレス／ポートでクライアント接続を受け付け、固定の中継先へセッション単位で接続する外部動作を定義する。 |
| 入力・前提 | CLI で確定した待受先、中継先、接続タイムアウト。クライアントからの TCP 接続。 |
| 処理・規則 | 待受ソケットをキャプチャ初期化より先に確保する。受付後はセッション ID を割り当て、中継先への接続待ちが他のクライアント受付を阻害しないようにする。 |
| 出力・結果 | 接続成功時は中継処理へ進む。待受処理は後続接続を継続して受け付ける。 |
| 異常系 | 待受失敗はプロセス起動失敗。中継先への接続失敗は当該セッションだけを終了し、待受処理は継続する。 |
| 関連仕様 ID | `EXT-NET-001`..`EXT-NET-004`, `AC-NET-001`, `AC-NET-002` |

### 4.1 待受側・中継先 — `EXT-NET-001`

- 指定したローカルアドレス／TCP ポートで待ち受ける。既定は `127.0.0.1:8080` とする。
- 中継先はプロセス起動時に指定した固定ホスト／ポートとし、既定は `localhost:80` とする。
- 外部ホストから接続させる場合は、`--listen-host` でワイルドカードアドレスまたは特定のインターフェースアドレスを明示する。
- 既定では全インターフェースへ公開しない。

### 4.2 待受処理の起動順序 — `EXT-NET-002`

待受ソケットのバインドを、キャプチャファイルの作成より先に完了します。

待受アドレス／ポートを確保できない場合は、指定されたキャプチャファイルを新規作成・変更しません。

### 4.3 クライアント受付・中継先への接続 — `EXT-NET-003`

- クライアント接続を受け付けると、プロセス内で一意なセッション ID を割り当て、中継先への接続を開始する。
- あるセッションで中継先への接続待ちが発生していても、待受処理は後続のクライアント接続を受け付けられる状態を維持する。
- 中継先への接続には、`--connect-timeout` の指定値をタイムアウトとして使用する。

### 4.4 中継先への接続失敗 — `EXT-NET-004`

中継先への接続に失敗した場合は、次の動作とします。

- 当該セッションのクライアント側／中継先側ソケットを終了する。
- 待受処理は終了せず、後続接続の受付を継続する。
- キャプチャが有効なら、失敗をネットワーク上の実パケットに変換せず、`CONNECT_ERROR` 診断イベントとしてキャプチャに記録する。

## 5. 主要機能・中継仕様

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |
| 目的 | 接続済みクライアントと中継先の TCP バイトストリームを、内容と順序を変えず双方向に中継する。 |
| 入力・前提 | クライアント側／中継先側の接続済み TCP ストリーム。 |
| 処理・規則 | 2方向を独立して中継する。入力から読み取った時点をキャプチャの観測点とし、反対側への書込み成功分だけを転送済みバイト数とする。読取り単位をパケット／メッセージ境界と解釈しない。 |
| 出力・結果 | 反対側へ同一バイト列を順序どおり中継する。一方向の EOF は反対側の出力をハーフクローズし、逆方向は継続する。 |
| 異常系 | 中継 I/O エラーは当該セッションのソケットを終了させるが、待受処理は継続する。 |
| 関連仕様 ID | `EXT-RELAY-001`..`EXT-RELAY-003`, `AC-RELAY-001`, `AC-RELAY-002`, `AC-CAP-005` |

### 5.1 双方向バイトストリーム中継 — `EXT-RELAY-001`

接続確立後は、クライアントから中継先と、中継先からクライアントのバイトストリームを独立して中継します。

- 各方向で読み取ったアプリケーションのバイト列を、順序を変えず反対側へ書き込む。
- バイト数は、反対側ソケットへの `write` に成功したバイト数を基準とする。
- キャプチャへ記録するデータは、各方向の入力ストリームから正常に読み取ったバイト列を基準とし、その後の反対側ソケットへの `write` の成否には依存しない。
- 読取り単位を TCP パケット境界またはアプリケーションメッセージ境界とみなさない。

TcpTap が観測・中継できるのは、OS が再構成した TCP バイトストリームです。キャプチャの観測点は TcpTap が入力ストリームからバイト列を読み取った時点であり、そのバイト列が反対側へ配送されたことまでは表しません。元の通信パケットの境界や、トランスポート層のメタデータは外部契約に含みません。

### 5.2 EOF・ハーフクローズ — `EXT-RELAY-002`

一方向が EOF になった場合は、その方向に対応する反対側の出力をハーフクローズし、逆方向の中継は直ちには終了させません。

両方向が終了した後にセッションを終了します。

### 5.3 中継中の I/O エラー — `EXT-RELAY-003`

中継中の I/O エラーでは、当該セッションのソケットを終了させ、反対方向で待機中の I/O も終了させます。

当該セッションのエラーによって待受処理は終了させません。

## 6. 出力・ログ・観測仕様

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |
| 目的 | TcpTap が中継処理で直接観測した状態・セッション情報を、人間が追跡できる標準出力／標準エラーとして提供する。 |
| 入力・前提 | 待受開始、クライアント受付、中継先接続、EOF、I/O エラー、セッション終了、キャプチャ状態などの観測事実。 |
| 処理・規則 | セッション ID、時刻、経過時間、方向別バイト数、終了理由を定めた形式で出力する。外部入力を埋め込むときは CR / LF を空白へ置換する。 |
| 出力・結果 | 通常イベントは標準出力、CLI／起動／キャプチャ警告・エラーは標準エラーへ出力する。 |
| 異常系 | 起動／待受エラーには `STARTUP_OR_LISTENER_ERROR` を含める。通常エラーで Java のスタックトレースを利用者向け出力へ表示しない。 |
| 関連仕様 ID | `EXT-OBS-001`, `EXT-CLI-003`, `EXT-NET-004`, `EXT-RELAY-003` |

### 6.1 セッションの観測情報 — `EXT-OBS-001`

TcpTap が通常の中継処理で直接観測する事実は次のとおりです。

| 観測項目 | 内容 |
| --- | --- |
| エンドポイント | クライアント／中継先のアドレスとポート |
| 受付 | クライアント接続を受け付けた時点 |
| 接続 | 中継先への接続成否と所要時間 |
| 観測データ | 各方向で入力ストリームから読み取ったバイト列 |
| 転送量 | 各方向で反対側への中継に成功したバイト数 |
| 終了事象 | 各方向の EOF または Java ソケット／ストリームの I/O エラー |
| 継続時間 | セッションの開始から終了までの経過時間 |

セッション ID は、受け付けたセッションごとにプロセス内で増加する正の番号とし、通常出力では `#000001` のように最低6桁で表示します。

### 6.2 標準出力

通常の状態・セッションイベントは、概ね次の形式で標準出力へ出力します。

```text
<timestamp> CAPTURE file=<path> mode=reconstructed-stream
<timestamp> LISTEN <local-endpoint> -> <destination> connect_timeout=<millis>ms
<timestamp> #<session> ACCEPT client=<endpoint>
<timestamp> #<session> CONNECT destination=<endpoint> <millis>ms
<timestamp> #<session> CONNECT_ERROR destination=<destination> <millis>ms <Exception>: <message>
#<session> <C->D|D->C> ERROR <Exception>: <message>
#<session> CLOSE duration=<seconds>s c2d=<bytes>B d2c=<bytes>B c2d_end=<reason> d2c_end=<reason>
```

- 時刻を伴うイベントは ISO-8601 の `Instant` 表現を使用する。
- `CONNECT` の所要時間はミリ秒、`CLOSE` の継続時間は秒で小数3桁表示する。
- `CLOSE` は、中継先への接続成功後の中継セッションについて、両方向の処理が終了した後に出力する。
- 終了理由は、正常 EOF では `EOF`、I/O エラーでは `IO_ERROR:<ExceptionSimpleName>` とする。
- ホスト、パス、例外メッセージなどをログへ埋め込む場合は、CR / LF を空白へ置換し、1イベントを複数行へ分断させない。

### 6.3 標準エラー

CLI の指定エラー、プロセス全体の起動／待受エラー、キャプチャ書込み処理の警告／エラーは、標準エラーへ出力します。

起動／待受エラーには `STARTUP_OR_LISTENER_ERROR` を含めます。

## 7. ファイル・キャプチャ仕様

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |
| 目的 | TcpTap が直接観測したストリームと診断イベントを、実パケットのキャプチャと誤認しない形で pcapng に保存する。 |
| 入力・前提 | `--capture <FILE>` の指定、接続済みセッションの観測データ、EOF／I/O エラー、中継先接続失敗の診断情報。 |
| 処理・規則 | ファイルは新規作成のみ。再構成ストリームと診断イベントを別インターフェースへ格納し、観測していないネットワーク事象を推測して生成しない。 |
| 出力・結果 | Wireshark で開ける pcapng。再構成用 `LINKTYPE_RAW` と診断用 `LINKTYPE_USER0` を含む。 |
| 異常系 | 初期化失敗は起動失敗。稼働中の書込み失敗はキャプチャだけを停止し、TCP 中継は継続する。 |
| 関連仕様 ID | `EXT-FILE-001`, `EXT-CAP-001`..`EXT-CAP-003`, `AC-FILE-001`, `AC-CAP-001`..`AC-CAP-005` |

`--capture <FILE>` を指定した場合だけ pcapng を生成します。

### 7.1 ファイルのライフサイクル — `EXT-FILE-001`

- キャプチャファイルは新規作成だけを許可し、既存ファイルを切り詰めたり上書きしたりしない。
- 既存ファイルを指定した場合は起動を失敗させ、そのファイルの内容を変更しない。
- 待受ソケットのバインドが失敗した場合は、キャプチャファイルを作成しない。
- 待受ソケットのバインド成功後にキャプチャファイルを初期化し、初期化に失敗した場合はプロセス全体のエラーとして起動を失敗させる。
- キャプチャに必要なエンドポイントアドレスを取得できない接続済みセッションは、擬似ストリームのキャプチャを行わず、中継を継続する。

キャプチャファイルにはアプリケーションのペイロードが含まれ得ます。通信内容に認証情報、トークン、個人情報、機密情報などが含まれる場合、キャプチャファイルも同等の機密性を持つものとして扱う必要があります。

### 7.2 pcapng 構成 — `EXT-CAP-001`

このキャプチャは実際のパケットキャプチャではありません。同一 pcapng セクション内で、擬似 TCP 通信と TcpTap 自身が直接観測した診断イベントを別インターフェースに分離します。

| 項目 | 再構成ストリーム | 診断イベント |
| --- | --- | --- |
| インターフェース ID | `0` | `1` |
| LinkType | `LINKTYPE_RAW` | `LINKTYPE_USER0` |
| インターフェース名 | `tcptap-reconstructed` | `tcptap-diagnostics` |
| 主な内容 | 擬似 IPv4 / IPv6 TCP パケット | UTF-8 JSON の診断イベント |
| 主な用途 | アプリケーション内容確認、Follow TCP Stream | TcpTap が直接観測したセッション障害の確認 |

共通の構成規則は次のとおりです。

- pcapng の Section Header Block、Interface Description Block、Enhanced Packet Block を使用する。
- Section Header のコメントには、擬似 TCP/IP ヘッダー、シーケンス番号、パケット境界、時刻、および診断イベントが、ネットワーク上の実パケットをキャプチャしたものではないことを記録する。
- 診断用 Enhanced Packet Block には、人間が読めるパケットコメントを付ける。
- Wireshark 専用のプラグイン／ディセクターを通常利用の前提にしない。

### 7.3 再構成ストリーム

中継先への接続成功後にストリームのキャプチャを開始したセッションでは、次を生成します。

| 観測事象 | 擬似表現 |
| --- | --- |
| 接続開始 | `SYN` / `SYN+ACK` / `ACK` |
| 入力ストリームから読み取ったペイロード | `PSH+ACK` |
| EOF | `FIN+ACK` |
| 中継中の I/O エラー | `RST+ACK` |

擬似シーケンス番号／確認応答番号は、セッション内でペイロード長と FIN を反映して一貫させますが、実際の接続で使われた値ではありません。ペイロードは TcpTap が読み取った時点で観測済みとして記録するため、その後の反対側への `write` が失敗した場合でもキャプチャに残ります。したがって、キャプチャに存在するペイロードは反対側アプリケーションへの配送成功を意味しません。

- 擬似 IPv4 ヘッダーのチェックサムと TCP チェックサム、IPv6 TCP チェックサムは、生成内容に対して正しく計算する。
- クライアント／中継先がともに IPv4 の場合は IPv4 パケットとする。
- いずれかが IPv6 の場合は IPv6 パケットとし、必要な IPv4 エンドポイントは IPv4-mapped IPv6 アドレスとして表現する。
- 時刻はキャプチャイベントを生成した時点の値であり、ネットワーク上で実パケットが流れた時刻ではない。

### 7.4 診断イベント — `EXT-CAP-002`

中継先への接続に失敗した場合は、`CONNECT_ERROR` 診断イベントを記録します。

| フィールド | 内容 |
| --- | --- |
| スキーマバージョン | 診断データ形式のバージョン |
| イベント種別 | `CONNECT_ERROR` |
| セッション ID | 当該接続に割り当てたセッション ID |
| 中継先 | 設定された中継先。CR / LF を空白へ置換した後、UTF-16 code unit 数で 4096 を上限とし、超過時は先頭 4093 code unit に `...` を付けた値へ切り詰める。 |
| 例外 | 例外の単純名 |
| メッセージ | CR / LF を空白へ置換した例外メッセージ。UTF-16 code unit 数で 4096 を上限とし、超過時は先頭 4093 code unit に `...` を付けた値へ切り詰める。 |

切り詰めは JSON エスケープより前の値に対して行います。4096 code unit 以下の値は切り詰めません。同じ切り詰め済みの中継先／メッセージを、診断用 Enhanced Packet Block の JSON と人間向けパケットコメントに使用します。

`CONNECT_ERROR` は、TcpTap／Java ソケット API が観測した失敗を表します。ネットワーク上の SYN、RST、ICMP、ファイアウォール動作などを推測したパケットは生成しません。

### 7.5 キャプチャ障害の分離 — `EXT-CAP-003`

稼働中にキャプチャへの書込みが失敗した場合は、以後のキャプチャ出力を停止しますが、TCP の中継自体は継続します。

### 7.6 キャプチャで表現できない事項

通常の中継／キャプチャから、次を実パケットの事実として取得・推測しません。

- 元パケットの境界
- 実 TCP のシーケンス番号／確認応答番号
- 再送／重複 ACK／パケット損失
- 受信ウィンドウ／輻輳ウィンドウ
- IP TTL／フラグメンテーションの実値
- ネットワーク上の実パケットの時刻
- キャプチャ済みペイロードが反対側アプリケーションへ配送されたかどうか
- 中継先への接続失敗時にネットワーク上で発生した SYN／RST／ICMP などの具体的なパケット列

擬似 TCP インターフェースは、アプリケーションプロトコルのディセクターや Follow TCP Stream による内容確認を目的とします。診断インターフェースは、TcpTap が直接観測したセッション障害の確認を目的とします。どちらもトランスポート層／ネットワーク層の実パケット障害解析には使用しません。

## 9. 非機能・セキュリティ・制約

### 設計単位サマリ

| 項目 | 内容 |
| --- | --- |

| 入力・前提 | JRE、OS／ネットワークの到達制御、TcpTap が中継するアプリケーションデータ、任意のキャプチャ保存先。 |
| 処理・規則 | JRE 8 互換を維持し、既定待受をループバックに限定する。TcpTap 自身に認証・認可機能を持たせず、実パケットとして観測していない情報を事実として提示しない。 |
| 出力・結果 | 単独実行可能な JAR と、明確なセキュリティ／利用上の境界。 |
| 異常系 | 最大接続数・スループット等は現時点で保証値を持たない。必要になった場合は測定条件と受入条件を追加する。 |
| 関連仕様 ID | `EXT-ENV-001`, `EXT-SEC-001` および各章の外部不変条件 |

### 9.1 動作環境・配布 — `EXT-ENV-001`

- 最低動作環境は JRE 8 とする。
- 配布 JAR は Java 8 のバイトコード／Java SE 8 API 互換性を維持する。
- `TcpTap.jar` は単独で起動でき、利用者に実行時依存ライブラリの追加配置を要求しない。
- インストーラー、Npcap / libpcap、パケットキャプチャ権限を通常利用の前提にしない。

### 9.2 セキュリティ／信頼境界 — `EXT-SEC-001`

TcpTap は、認証プロキシやアクセス制御ゲートウェイではありません。

- 待受ポートへ到達したクライアントについて、TcpTap 自身は本人確認、認可、接続元許可リスト、レート制限などを行わない。
- 外部インターフェースへバインドする場合の到達制御は、OS のファイアウォールやネットワークポリシーの責務とする。
- 中継処理ではアプリケーションのペイロードをバイト列として扱う。
- TLS などで暗号化済みのペイロードは暗号化されたまま中継するが、TcpTap 自身がペイロードに追加の機密性・完全性保護を与えるものではない。
- キャプチャファイルの保存先、アクセス制御、保管期間、安全な削除は利用環境の責務とする。

### 9.3 性能・規模上の位置付け

TcpTap は軽量な診断用中継ツールを目的とし、大量接続を処理する高密度プロキシを目的としません。

現時点では、最大同時接続数、スループット、メモリ使用量などを保証値として外部仕様化しません。保証値が必要になった場合は、測定条件と受入条件を定義して本章へ追加します。

### 9.4 外部仕様上の重要な不変条件

| 分類 | 不変条件 | 主な関連仕様 |
| --- | --- | --- |
| 待受 | 既定の待受アドレスをループバックに限定する。 | `EXT-NET-001`, `EXT-SEC-001` |
| 中継 | アプリケーションのペイロードを変更せず双方向に中継する。 | `EXT-RELAY-001` |
| EOF | ハーフクローズを保持し、片方向の EOF だけで逆方向の中継を即時終了しない。 | `EXT-RELAY-002` |
| 障害分離 | 中継先への接続失敗をセッション単位に閉じ、待受処理を継続する。 | `EXT-NET-004` |
| 観測点 | キャプチャのペイロードは TcpTap が入力ストリームから観測したバイト列を基準とし、反対側への配送成功を表すものとしない。 | `EXT-RELAY-001`, `EXT-CAP-001` |
| 診断 | 中継先への接続失敗時は、観測していない実パケットを生成せず診断イベントとして残す。 | `EXT-CAP-002` |

| 識別 | 擬似キャプチャを実パケットのキャプチャと誤認できないよう、ファイル自体にも識別情報を持たせる。 | `EXT-CAP-001` |
| 観測限界 | 実パケットとして観測していないトランスポート層／ネットワーク層のメタデータを事実として提示しない。 | `EXT-CAP-001`, `EXT-CAP-002` |

## 10. 受入条件

受入条件は、実装詳細ではなく外部から観測できる「前提／操作／期待結果」で定義します。

### 10.1 CLI 入力検証 — `AC-CLI-001`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-CLI-001`, `EXT-CLI-002`, `EXT-CLI-003` |
| 前提 | TcpTap を CLI から起動する。 |
| 操作 | ヘルプ、ポート境界値、不正ポート、不正タイムアウト、空白値、未知オプション、重複オプション、旧オプション名をそれぞれ指定する。 |
| 期待結果 | ヘルプと正しい境界値だけを受け付け、不正指定は待受処理を開始せず CLI の指定エラーとする。ヘルプの終了コードは `0`、指定エラーは `2` とする。 |

### 10.2 待受処理の起動失敗 — `AC-NET-001`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-NET-002`, `EXT-FILE-001` |
| 前提 | 指定した待受アドレス／ポートがすでに使用され、存在しないパスの `--capture` を指定する。 |
| 操作 | TcpTap を起動する。 |
| 期待結果 | 終了コード `1` で起動に失敗し、`STARTUP_OR_LISTENER_ERROR` を標準エラーへ出力し、キャプチャファイルを作成しない。 |

### 10.3 中継先接続処理の待受分離 — `AC-NET-002`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-NET-003`, `EXT-NET-004`, `EXT-CAP-002` |
| 前提 | 待受処理は起動済みである。中継先への接続が完了せず待機しているケースと、中継先への接続が失敗するケースをそれぞれ用意する。接続失敗時のキャプチャは有効とする。 |
| 操作 | 1つ目のクライアントを TcpTap へ接続し、そのセッションの中継先接続が待機中の間、または接続失敗後に、後続クライアントを TcpTap へ接続する。 |
| 期待結果 | 中継先への接続待ちによって待受処理を阻害せず、後続クライアントを受け付ける。中継先への接続失敗は当該セッションだけを終了し、`CONNECT_ERROR` 診断イベントを記録した後も待受処理を継続し、さらに後続クライアントを受け付けられる。 |

### 10.4 双方向中継とハーフクローズ — `AC-RELAY-001`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-RELAY-001`, `EXT-RELAY-002` |
| 前提 | クライアント、TcpTap、中継先の TCP 接続が確立している。 |
| 操作 | クライアントと中継先がそれぞれペイロードを送信し、その後片方向ずつ出力を終了する。 |
| 期待結果 | ペイロードは両方向でバイト単位に同一のまま到達する。一方向の EOF は反対側へ EOF として伝播し、もう一方向はその EOF だけを理由に失われない。両方向終了後にセッションが終了する。 |

### 10.5 既存キャプチャファイル — `AC-FILE-001`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-FILE-001` |
| 前提 | `--capture` に既存ファイルを指定する。 |
| 操作 | TcpTap を起動する。 |
| 期待結果 | プロセス全体のエラーとして起動に失敗し、既存ファイルの内容を変更しない。 |

### 10.6 再構成ストリームの表現 — `AC-CAP-001`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-CAP-001`, `EXT-RELAY-001`, `EXT-RELAY-002` |
| 前提 | キャプチャが有効な接続済み IPv4 セッションがある。 |
| 操作 | クライアント／中継先の両方向からペイロードを読み取り、中継し、両方向が EOF になる。 |
| 期待結果 | pcapng は再構成用インターフェースと診断用インターフェースを持ち、再構成用インターフェースに擬似ハンドシェイク、TcpTap が観測した両方向のペイロード、FIN を一貫したチェックサム／シーケンス状態で保存する。Section Header には、実際の通信をキャプチャしたものではないことを識別できる情報を持たせる。 |

### 10.7 接続エラーの診断 — `AC-CAP-002`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-CAP-001`, `EXT-CAP-002` |
| 前提 | キャプチャが有効で、中継先への接続が失敗する。診断値については、4096 code unit の値と 4096 code unit を超える値を用意する。 |
| 操作 | TcpTap が失敗を観測する。 |
| 期待結果 | 診断用インターフェースの Enhanced Packet Block に、スキーマバージョン、`CONNECT_ERROR`、セッション ID、中継先、例外、無害化済みメッセージを UTF-8 JSON として保存し、人間が読めるパケットコメントを付ける。中継先／メッセージは 4096 code unit 以下なら保持し、超過時は先頭 4093 code unit と `...` に切り詰める。再構成用インターフェースに、未観測の SYN／RST／ICMP などを生成しない。 |

### 10.8 中継 I/O エラーの分離 — `AC-RELAY-002`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-RELAY-003`, `EXT-OBS-001`, `EXT-CAP-001` |
| 前提 | クライアント、TcpTap、中継先の接続が確立し、キャプチャが有効である。 |
| 操作 | 中継中の一方向で Java ソケット／ストリームの I/O エラーが発生する。 |
| 期待結果 | 当該セッションのソケットを終了して両方向の中継を終了し、該当方向の終了理由を `IO_ERROR:<ExceptionSimpleName>` とする。キャプチャには該当方向の擬似 `RST+ACK` を記録する。 |

### 10.9 キャプチャ書込み失敗の分離 — `AC-CAP-003`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-CAP-003`, `EXT-RELAY-001`, `EXT-RELAY-002` |
| 前提 | キャプチャが有効な接続済みセッションがあり、双方向中継が可能である。 |
| 操作 | 稼働中のキャプチャ書込みが失敗する。 |
| 期待結果 | 以後のキャプチャ出力を停止するが、アプリケーションのペイロードの双方向中継、ハーフクローズ、セッション終了は継続する。キャプチャ障害を中継の I/O エラーとして扱わない。 |

### 10.10 IPv6 再構成ストリームの表現 — `AC-CAP-004`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-CAP-001` |
| 前提 | キャプチャが有効な接続済みセッションで、一方のエンドポイントが IPv6、他方が IPv4 である。 |
| 操作 | 擬似通信とペイロードをキャプチャする。 |
| 期待結果 | 再構成用インターフェースには IPv6 パケットを生成し、IPv4 エンドポイントは IPv4-mapped IPv6 アドレスで表現する。生成した IPv6 TCP チェックサムは正しい。 |

### 10.11 観測後の中継失敗でもペイロードを保持 — `AC-CAP-005`

| 項目 | 内容 |
| --- | --- |
| 対象仕様 | `EXT-RELAY-001`, `EXT-RELAY-003`, `EXT-CAP-001` |
| 前提 | キャプチャが有効な接続済みセッションがある。 |
| 操作 | 一方向の入力ストリームからペイロードを正常に読み取った後、そのペイロードの反対側ソケットへの `write` が I/O エラーになる。 |
| 期待結果 | 読み取ったペイロードは TcpTap が観測したデータとしてキャプチャに保存し、該当方向の擬似 `RST+ACK` も記録する。終了要約の転送済みバイト数には `write` に成功していないバイトを加算しない。 |
